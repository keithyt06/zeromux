# PM 审 S6 / S7 spec(2026-09-29)

对象:`specs/2026-09-29-s6-gate-review-dispatch-design.md`(下称 S6)、`specs/2026-09-29-s7-crew-cockpit-and-backend-parity-design.md`(下称 S7)。
对照:路线图 `kiro-final-roadmap`、调研 §7、总 spec R20/R22/M12、S3 V14。只审,不改 spec。

总评:工程核实非常扎实,R22、M12 和「不加顶层导航」都守住了。问题集中在四处:北极星指标测不出来;门槛 T 的口径互相打架;预检退出码的方向与唯一的配方相反;几处「叫醒之后点不进去」。

## BLOCKER

**B1 北极星「等人时长」无法测量,S6 也没有成功指标**
- 位置:S6 全文(没有「成功指标」一节);S7 §11.2。
- 问题:`zmx_read.lastViewedMs` 只存在 localStorage,并且每看一次就被覆盖,取不到历史间隔。两份 spec 都没有任何埋点,S6 做完无法判断「收结果」是否变快。
- 建议:把 S7 §10 的 `POST /api/sessions/{id}/read` **提前到 S6**(它本来就是 S 级)。服务端写入时,如果 `last_outcome_ms > 旧 read_ms`,打一条 `tracing::info!(target:"zmx_usage","wait_ms={read-outcome} kind={outcome} sched={bool}")`,口径与 S7 T 的 journalctl 一致。S6 增加 §成功指标:等人时长 p50/p90 在 S6 上线前后各取 14 天对比;预检 skipped 率;F5 入库→派发中位时长。

**B2 预检退出码方向(S6 D1)与路线图唯一的配方相反**
- 位置:S6 §0.2 D1、§2.3、§2.6 文案。
- 问题:D1 规定 exit 0 = 跳过。但机器侧 backlog 的配方是 `gh issue list … | jq -e 'length>0'`(CTO ④⑦,路线图「不做」一节),它**在有活干时 exit 0**,按 D1 会被跳过,整条 Stage 4 配方随之失效。`grep -q`、`test`、`jq -e` 这类惯用写法同样都是「条件成立 = 0」。D1 声称「沿用 PM Q2」,但 Q2 并没有规定退出码。
- 建议:改为 **exit 0 = 唤醒,exit 1 = 跳过,其他(含 126/127、信号、超时、无法 spawn)= 预检故障**。表单文案同步改为「条件成立(退出 0)→唤醒 agent;退出 1→跳过本次」,「测试预检」的结果文案不变。实施前改好,成本为零;上线后再改就要迁移用户已有的命令。

**B3 门槛 T 有两套口径,计时起点也不公平**
- 位置:S6 §9.1 与 S7 §0.1。
- 问题:
  ① S6 用 `zeromux.db` 里的 `crew_mode` 加 `lifetime_turns>0` 人工查询;S7 用 journalctl `zmx_usage`。两者会得出不同结论。而且 S6 §3.2 让话题模式**跳过 metric**,`lifetime_turns` 在 `record_run_metric`(`session_manager.rs:847`)里累加,话题会话将永远为 0,S6 的口径会系统性少计。
  ② S6 §0.1 规定「并行话题」chip 要到 S6 T3 才上线,可 T 从 S5 G1+G2 上线就开始计 14 天。窗口内实际只有「目标指挥」可用,对话题模式不公平。
- 建议:以 S7 §0.1 的 journalctl 口径为**唯一口径**,S6 §9.1 改为引用它。计时起点改为「两个 chip 都可用之日」(即 S6 T3 上线日)。另外要求 3 次分布在 ≥2 个不同日期,避免一次尝鲜就把门槛刷过。G9 不受 T 约束,同意主会话的裁定。

## MAJOR

**M1 推送点进去什么也做不了(S6 G7 外部 slot、Crew cron 失败)**
- 位置:S6 D9、§4.3(推送的 `session_id` 为空,点击打开根路径);Crew cron 的只读视图要到 S7 才有。
- 问题:D9 的理由是「点了没反应的行比不放更糟」,但同一种推送点开后落在分诊首页,仍然没有可操作的东西,等于违反了 D9 自己的原则。
- 建议:外部 slot 推送的正文末尾写明去哪里回答(「在 Crew/微信回答」),SW 点击打开离开卡并展开该行。Crew cron 失败推送带 `?panel=scheduled&seg=crew` 深链,并把 **S7 §5 G9 挪到与 S6 T4 同期**(它不受 T 约束、规模 S,且与 T4 共用同一个数据源)。

**M2 F7「采纳」重启后基本失效,而且不导向下一步**
- 位置:S6 §5.1-5.2、D13。
- 问题:verdict 只存在内存。早上 review 的正是夜里跑出的结果,而夜里常有 auto-update 重启,「采纳」会高频弹出「未记录」toast。「已采纳 ✓」只是组件本地状态,刷新就丢,对用户几乎没有价值。
- 建议:本期把「采纳」定义为 **✓ 并直接打开「提交…」**(当 files>0 时),否则只显示 ✓。遇到 404 时静默,不弹 toast。verdict 能否写入降为 best-effort,不向用户承诺。同时去掉「提交…」上的 `confirmDanger`:现有 GitViewer 提交不需要确认(`GitViewer.tsx:382`),只有撤销需要。这样手机上 review 一轮是 2 击。

**M3 批量派发的「目标」在分诊里会消失(J2)**
- 位置:S6 §8.2。
- 问题:目标写进 description,而 TriageRow 第二行只在没有 snippet 和 step 时才显示 description(`TriageRow.tsx:39`)。agent 一跑起来,「哪几个属于同一目标」就看不出来了。
- 建议:TriageRow 第一行名称后加一个 `Badge`(描述以「目标：」开头时显示 X,最多 8 个字),并纳入 `same()` 比较。或者派发时把会话名改为 `X·<序号>`。二选一,都不需要改后端。

**M4 待派发不跨设备,J2 的主路径断了**
- 位置:S6 §7.2、§0.3。
- 问题:典型场景是在手机上随手记,回到桌面再派发。localStorage 版本在桌面上看不到手机记的条目。路线图接受了 localStorage,但当时没有点破这一点。
- 建议:请用户拍板。选项 A:保留 localStorage,并在「待派发」组标题注明「仅本设备」。选项 B:复用 quick_targets 同款的单表(约 1 个 S 级 task)。PM 倾向 B;若选 A,必须显式写入决策记录。

**M5 跨设备已读应提前**
- 位置:S7 §10。
- 问题:用户在手机和 Mac 上用得差不多多,「手机读过,桌面还显示完成·未读」是每天都会遇到的噪音,而且它是 B1 的数据源。
- 建议:从 S7-a 挪到 S6,与 B1 合并成一个 task。

**M6 S7-a 悄悄扩大了范围:Crew 的定时移植先于 T**
- 位置:S7 §6(标题「同一套移植也覆盖 Crew」)、§12 S7-a。
- 问题:路线图里 ② 只包括 Codex。Crew fan-out 的移植只服务于 G10,而 G10 受 T 约束。未过 T 就先做三后端 parity 这类历史上最容易出错的工作,可能白做。
- 建议:S7-a 只移植 Codex,Crew 部分挪到 S7-f。两者都走 `settle_scheduled_run` 抽取,后补 Crew 的成本很低。
