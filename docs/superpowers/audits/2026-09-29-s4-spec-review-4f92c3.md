### 1.3 S4 漏掉、但手机用户会实际遇到的问题

**A. 重连后回看状态不复位(P1,来自 9-26 期的 deferred 项)**
- 现状:WS 重连后 `scrollingRef`、`appScrollRef`、`newLines` 都不复位,`scroll_watch` 也不重新下发。手机锁屏、切 App、弱网都会触发重连。
- 后果:浮标可能卡在「回到底部 / N 行新输出」(`TerminalView.tsx:665`),而服务端 pane 其实早已不在 copy-mode;反过来也可能发生。
- 修法:
  - `onopen` 时复位上述 state。
  - **仅当断线前 `scrollingRef` 为真时**,onopen 后再发一次 `{type:'scroll', op:'cancel'}`。在 copy-mode 外它是 no-op(`cancel_outside_copy_mode_is_noop` 测试);AppWheel 下 Cancel 不产生任何滚轮字节,也是 no-op。
- 副作用:cancel 作用于整个 pane,会把 VSCode 端同一会话里正在进行的 copy-mode 一起退出。只在断线前本端正处于回看状态时才发,可以把这个影响降到最低。
- 放在 Task 1.5,即 Task 2 抽 hook 之前,避免 hook 的 `onOpen` / `onScrollState` 契约把现在的缺陷固化下来。
- 这不会破坏 Task 1 已有的断言:计划中的 characterization 按 `type` 过滤 input/resize 帧。

**B. 全屏 CLI 下浮标卡住,「发给」只能发出当前一屏(P0)**
- 浮标卡住的原因:AppWheel 模式下 Claude Code 不回报自己的滚动位置。`pillFromScrollState` 遇到 `down` 时保持现状,所以用户用手指滑回底部,浮标也不会消失。
- 只发出一屏的原因:用户手动开了全屏 Claude,或者 attach 的旧 shell 早于 T16、没有继承那个环境变量时,V5 一击拿到的内容只有当前一屏。
- 建议:
  - **浮标**:前端累计本轮手势的净滚动行数(up 加,down 减),净值 ≤ 0 时收起。3s 无操作时**不隐藏**,只降级为「仅 ⤓ 图标的描边按钮」。
  - 视觉区分:copy-mode(服务端确认的状态)用实心 accent;AppWheel(前端推测的状态)用描边。
  - 动画时长走 `--dur-*`,在 `prefers-reduced-motion` 下不做动画。
  - **全屏模式下的「发给」**:按钮文案保持「发给 〈目标名〉」。在按钮上方加一行 `text-ui-2xs`「仅当前屏」,颜色与现有黄色横幅一致。`aria-label` 写全「发给 〈目标名〉,仅当前屏」。
  - 不要把长后缀塞进按钮:390px 宽下底栏已有 5 个按钮,会溢出。★ 读屏时会被读作「黑星」,也不要作为唯一标识。

**C. 键栏 PgUp/PgDn 与 tmux 回看是两套机制(P3,需服务端路由,另起一项)**
- 实测:
  - 外层发 `ESC[5~`,tmux 不会进入 copy-mode(`in_mode=0`),按键交给应用。
  - copy-mode 下外层发 `^C`,会退出 copy-mode,并把 `^C` 交给 shell。「回看时按 ^C」是安全的。
- 不能简单地「tmux 会话里 PgUp 一律改走 scroll」,原因有三:
  - less / man / vim 处于 alternate screen 但不开鼠标,`scroll_route` 会判为 CopyMode(`src/tmux.rs:229`),PgUp 被截走,应用自己的翻页就坏了;
  - PgDn 在 copy-mode 外是 no-op,会变成死键;
  - AppWheel 下 n=rows-2 大约是 30 个滚轮事件,Claude 每个事件滚多少行没有实测(**假设**)。
- bash 下 PgUp 的实际效果**未实测**(**假设**:`/etc/inputrc` 中 `\e[5~` 的绑定是注释掉的,可能是 no-op)。
- 可行方案:
  - 仅当 pane **不在** alternate screen 时,走 scroll 按页滚动;否则照旧发字节。
  - 键帽改为 `ChevronsUp/ChevronsDown`,`aria-label` 为 `scroll-page-up/down`,与 PgUp 字节语义区分开。
  - 第一次按下时出现浮标作为反馈;在底部按 PgDn 就退出回看。
- 需要服务端配合判断 alternate,不在 Task 4 里顺带做。等出现用户反馈再做。

**D. 键栏收起后可视高度与 tmux 窗口同步(P2,假设)**
- 计划 Task 4 已把 `collapsed` 并入 refit effect 的 deps,方向正确。
- 收起会让 rows 增加约 3 行,触发一次 SIGWINCH,inline 模式的 Claude 会整屏重画。这是预期行为。
- 现有的 50ms debounce(`TerminalView.tsx:607-611`)足以避免动画期间反复 refit。**假设**,未在真机验证动画。

**E. 一击发送去掉确认框后,发错无法撤回(P1)**
- V5 删掉了 `HistoryView.tsx:134` 的 confirm,那里原本包含「内容可能含密钥」的提醒。
- 去掉后,发错目标只能等 agent 开始跑。
- 建议仿照删除会话的 5s 撤销:发送后 toast 显示「已发给 〈名〉 · N 行」,带 3s「撤回」,撤回期满再真正调用 `sendPrompt`。
- 同时要在「发给」附近保留一行固定的密钥提示,SendToMenu 底部已有同款文案(分析 §B4)。

**F. 横屏、软键盘与复制(P2,假设)**
- 已有横屏分屏(`LANDSCAPE_MQ`)和 keyboardOpen refit 两条路径。键栏收起需要覆盖「横屏」和「软键盘弹起」两种组合:收起状态下弹出键盘,不应自动展开。
- 手机上 xterm 无法触摸选区(`touch-action:none`),复制只能进 HistoryView 长按。
- 给「发给」按钮加 `-webkit-touch-callout:none` 时(分析 §B3),只能加在按钮上,**不能**影响内容区,否则会把系统的复制菜单一起禁掉。

**G. 键栏布局与触控目标(P2)**
- 现状:`btnCls` 只有 `py-2`,高约 36px,没有使用 `--hit`。
- 第二页 8 个键加上切换键,在 390px 宽下每个约 34px。扩到 12 个键后,每个约 25px。
- 建议:
  - 第二页改为两行网格,或横向滚动;所有键加 `min-h-[var(--hit)]`。
  - 收起后的入口「⌃ 键栏」保留文字,且满足 44px;按钮带 `aria-expanded`。
  - 收起状态下打开 📜 历史再关闭,应恢复为收起状态。

## 2. v2 计划里与 tmux / xterm 实际行为冲突的地方

### 2.1 Home/End 的 DECCKM 分派在 tmux 下多余(计划 Task 4、分析 §B3)

- 外层依次发 `ESC[H`、`ESC OH`、`ESC[F`、`ESC OF`、`ESC[A`、`ESC OA`,内层 `cat -v` 实际收到:
  - 内层开了 DECCKM(`printf '\033[?1h'`,`keypad_cursor_flag=1`):`^[[1~ ^[[1~ ^[[4~ ^[[4~ ^[OA ^[OA`
  - 内层没开 DECCKM:`^[[1~ ^[[1~ ^[[4~ ^[[4~ ^[[A ^[[A`
  - 使用 zeromux 生成的 tmux.conf(`default-terminal tmux-256color`)时结果相同。
- 结论:tmux 先解析外层按键,再按**内层应用自己的**模式和 terminfo 重新编码。外层发 Home/End 的哪种形式都一样;方向键随内层 DECCKM 变化,但这个转换也由 tmux 完成。
- 已有的 `arrowSequence(key, applicationCursorKeysMode)`(`TerminalView.tsx:231`)读的是 xterm 自己的 DECCKM(tmux 作为外层程序会发 smkx `\e[?1h`,这一点已复测),与内层应用无关。它之所以没出过错,是因为 tmux 两种形式都接受。
- bash(readline)实测:通过外层 pty 客户端 attach 后发 CSI 形式和 SS3 形式的 Home/End,都得到 `Xecho abcdefY`。
- 边界:
  - `extended-keys` 在 zeromux conf 中未开,但 conf 会 `source-file ~/.tmux.conf`,用户可能自己开启。即便开启,它也只影响带修饰键的组合,不影响裸 Home/End。
  - 新建会话已经不会退回裸 shell(`src/session_manager.rs:1143`)。非 tmux 的裸 PTY 只剩历史遗留会话。
- **建议**:
  - 如果加 Home/End,硬编码 `\x1b[H` / `\x1b[F`,不新增 `homeEndSequence` 及其测试。
  - `xtermMock` 的 `modes` 补上 `applicationCursorKeysMode: false`,让读取显式化(分析 §B6)。

### 2.2 WS 重连与 refresh-client

- 服务端订阅之后 `tokio::spawn` 一个任务,50ms 后执行 `refresh-client -t <tty>`(`src/ws_handler.rs:110-118`),按 PTY 子进程的 pid 找到对应 tty。
- 前端 `onopen` 先 `term.reset()`(I-5),再发首次 resize。两者之间没有同步:
  - resize 若晚于 refresh 到达,tmux 会按新尺寸再重画一次,结果正确。
  - 视图隐藏时 resize 被 `shouldSendResize` 拦下(T17),重连后先按旧尺寸画;等视图切回 active 后强制重发尺寸(`lastDims={0,0}`),再重画一次。
- 计划 Task 1 已覆盖 active 与 hidden 两种 onopen,需保证断言「hidden 时 0 次 resize」。
- `reset()` 之后到 refresh 到达之前,可能会闪白约 50ms 加一次 RTT。这是已有行为,不在 S4 范围内。**假设**,未测量。

### 2.3 resize 与 `window-size latest`

- 计划的 Global Constraints 已列出 I-12(只有 active 且非 0×0 的视图可以发 resize),这与 T17 的行为一致,**不冲突**。
- **需要补充**:TerminalView 没有 ResizeObserver,refit 只由 window 的 resize 事件和几个 effect(keyboardOpen、split、wsStatus、active)触发。桌面 ContextPanel 展开/收起不会触发 window resize,所以**现在根本不会 refit**,必须显式接到 `handleResize`(总 spec §7 的「展开时一次 refit」目前没有落地路径)。
- `window-size latest` 复测:任何一个客户端 resize,窗口就跟随它。所以桌面缩放窗口或展开右栏,都会让手机上同一会话变窄。这是多端共享 tmux 的固有行为,放进 acceptance 的「已知行为」,不作为验收项。

### 2.4 onBinary 的 exitScroll:现状正确,计划描述需要更正

- 现状:`TerminalView.tsx:322-323` 的 `term.onBinary` 会先调 `exitScroll()`,这是 9-26 期 T6+T7 修复轮加上的,**没有缺陷**。
- 计划 Task 2 硬约束第 ③ 条写的是「`onBinary`/mouse/scroll/scroll_watch 本就绕过 sendInput,改走 hook 的 `sendRaw`,语义不变」。**这句话对 onBinary 不成立。**
- 处理:
  - Task 1 加一条 characterization:「回看状态下触发 onBinary,先发 cancel」;
  - Task 2 第 ③ 条更正为「onBinary 走 sendRaw 前仍须 `exitScroll()`」。
- 不需要进 Task 1.5。

### 2.5 tmux copy-mode 下的按键

`sendInput = exitScroll(); sock.sendInput(d)`(计划 Task 2)保留了「任何键先退出回看」的行为,是正确的。§1.3 C 的实测也表明,copy-mode 下的 `^C` 是安全的。
